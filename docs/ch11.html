第 11 章

基于工具的智能体

前面十章里，流程都是我们写死的：先检索，再生成。从这一章起把方向盘交给模型 —— 给它一组工具，由它自己决定用不用、用哪个、用几次。 我们会先手写一遍智能体的核心循环，看清每个齿轮怎么转，然后再换成一行就能搞定的预置组件。

本章目标

  • 理解「工具调用」的真相：模型只是提出请求，真正执行的是你的代码
  • 掌握 ReAct 模式：思考 → 行动 → 观察，循环往复
  • 用 LangGraph 从零搭一个单工具的旅行信息智能体
  • 扩展成多工具智能体，并用系统提示词引导它正确使用工具
  • 用预置的 ReAct 智能体把几十行代码缩成几行
  • 认识当前的标准写法 create_agent 和中间件机制

工具调用是怎么回事

第 1 章说过，LLM「只会说，不会做」。那它怎么查天气、查数据库？答案是一个约定好的协作协议，叫工具调用 （tool calling，早期叫 function calling）：

🔑 这一章最重要的一句话

模型不会执行任何东西。它只是输出一段结构化的文字：「我想调用 search_travel_info，参数是 {"query": "..."}」。 要不要执行、怎么执行、执行前要不要检查权限 —— 全部由你的代码决定。这也是智能体安全性的根基。

ReAct：思考、行动、观察

一次工具调用往往不够。问「推荐两个天气好的康沃尔海滨小镇」，得先查有哪些海滨小镇，再逐个查天气。 让这个过程循环起来的模式叫 ReAct（Reasoning + Acting）：

对比一下第 5 章：那里的循环条件是我们写的规则（相关性 < 50%）；这里循环是否继续由模型自己判断。这就是「工作流」和「智能体」的分水岭。

/** 下载 WikiVoyage 页面并建立向量库（这里用内存向量库，省去启动 Chroma 服务）。 */
async function buildVectorstore(destinations: string[]) {
  const splitter = new RecursiveCharacterTextSplitter({ chunkSize: 1024, chunkOverlap: 128 });
  const texts: string[] = [], metadatas: { source: string }[] = [];

  for (const slug of destinations) {
    const url = `https://en.wikivoyage.org/wiki/${slug}`;
    const $ = cheerio.load(await (await fetch(url)).text());
    $("script, style").remove();
    texts.push($("body").text());
    metadatas.push({ source: url });
  }
  const chunks = await splitter.createDocuments(texts, metadatas);
  console.log(`Embedding ${chunks.length} chunks ...`);
  return MemoryVectorStore.fromDocuments(chunks, new OpenAIEmbeddings());
}

const tiVectorstore = await buildVectorstore(UK_DESTINATIONS);
const tiRetriever = tiVectorstore.asRetriever();

import dev.langchain4j.store.embedding.inmemory.InMemoryEmbeddingStore;

public class TravelKnowledgeBase {
    static final List<String> UK_DESTINATIONS =
            List.of("Cornwall", "North_Cornwall", "South_Cornwall", "West_Cornwall");

    final EmbeddingModel embeddingModel = OpenAiEmbeddingModel.builder()
            .apiKey(System.getenv("OPENAI_API_KEY")).modelName("text-embedding-3-small").build();
    final EmbeddingStore<TextSegment> store = new InMemoryEmbeddingStore<>();

    /** 下载 WikiVoyage 页面并建立向量库。 */
    public TravelKnowledgeBase() throws IOException {
        var splitter = DocumentSplitters.recursive(1024, 128);
        for (String slug : UK_DESTINATIONS) {
            String url = "https://en.wikivoyage.org/wiki/" + slug;
            var doc = Document.from(Jsoup.connect(url).get().body().text(), Metadata.from("source", url));
            var chunks = splitter.split(doc);
            store.addAll(embeddingModel.embedAll(chunks).content(), chunks);
        }
    }

    public String search(String query) {
        var request = EmbeddingSearchRequest.builder()
                .queryEmbedding(embeddingModel.embed(query).content()).maxResults(4).build();
        return store.search(request).matches().stream()
                .map(m -> m.embedded().text())
                .collect(Collectors.joining("\n---\n"));
    }
}

定义工具

一个工具就是一个普通函数 + 一份给模型看的说明书。说明书包含三样：名称、用途描述、参数的名字和类型。 模型完全靠这份说明书判断「什么时候该用它、参数该填什么」。 

from langchain_core.tools import tool

@tool                                    # 装饰器把函数变成工具
def search_travel_info(query: str) -> str:
    """Search embedded WikiVoyage content for
    information about destinations in England."""      # ← 文档字符串就是给模型看的描述
    docs = ti_retriever.invoke(query)
    top = docs[:4] if isinstance(docs, list) else docs
    return "\n---\n".join(d.page_content for d in top)

💡 工具描述就是提示词

模型选不选这个工具、参数填得对不对，几乎完全取决于描述写得清不清楚。 把它当成写给一位新同事的说明：这个工具做什么、什么时候该用、每个参数是什么意思、返回什么。 后面会看到，描述含糊时模型会跳过工具，自己编答案。

class ToolsExecutionNode:
    """执行最后一条 AIMessage 里 LLM 请求的所有工具。"""

    def __init__(self, tools: Sequence):
        self._tools_by_name = {t.name: t for t in tools}

    def __call__(self, state: dict):
        last_msg = state["messages"][-1]
        tool_messages: list[ToolMessage] = []

        for tool_call in getattr(last_msg, "tool_calls", []):
            tool = self._tools_by_name[tool_call["name"]]       # 按名字找到函数
            result = tool.invoke(tool_call["args"])             # 用模型给的参数执行
            tool_messages.append(ToolMessage(
                content=json.dumps(result),
                name=tool_call["name"],
                tool_call_id=tool_call["id"]))                  # 必须带上 id，模型靠它对号入座

        return {"messages": tool_messages}                      # 追加到状态

tools_execution_node = ToolsExecutionNode(TOOLS)

def llm_node(state: AgentState):
    """LLM 节点：决定是调用工具，还是直接回答。"""
    response_message = llm_with_tools.invoke(state["messages"])
    return {"messages": [response_message]}

const toolsByName = Object.fromEntries(TOOLS.map((t) => [t.name, t]));

/** 执行最后一条 AIMessage 里 LLM 请求的所有工具。 */
async function toolsExecutionNode(state: AgentState) {
  const lastMsg = state.messages.at(-1) as AIMessage;
  const toolMessages: ToolMessage[] = [];

  for (const toolCall of lastMsg.tool_calls ?? []) {
    const selected = toolsByName[toolCall.name];                 // 按名字找到函数
    const result = await selected.invoke(toolCall.args);         // 用模型给的参数执行
    toolMessages.push(new ToolMessage({
      content: typeof result === "string" ? result : JSON.stringify(result),
      name: toolCall.name,
      tool_call_id: toolCall.id!,                                // 必须带上 id
    }));
  }
  return { messages: toolMessages };                             // 追加到状态
}

/** LLM 节点：决定是调用工具，还是直接回答。 */
async function llmNode(state: AgentState) {
  const responseMessage = await llmWithTools.invoke(state.messages);
  return { messages: [responseMessage] };
}

import dev.langchain4j.agent.tool.ToolExecutionRequest;
import dev.langchain4j.model.chat.request.ChatRequest;
import dev.langchain4j.service.tool.DefaultToolExecutor;

static String runAgent(ChatModel llm, Object tools, List<ToolSpecification> toolSpecs, String question) {
    List<ChatMessage> messages = new ArrayList<>();
    messages.add(UserMessage.from(question));

    while (true) {
        // —— LLM 节点：把全部消息 + 工具清单发给模型 ——
        AiMessage aiMessage = llm.chat(ChatRequest.builder()
                .messages(messages)
                .toolSpecifications(toolSpecs)
                .build()).aiMessage();
        messages.add(aiMessage);

        // —— 条件边：没有工具调用请求，就是最终答案 ——
        if (!aiMessage.hasToolExecutionRequests()) {
            return aiMessage.text();
        }

        // —— 工具节点：逐个执行，把结果作为「工具结果消息」追加 ——
        for (ToolExecutionRequest request : aiMessage.toolExecutionRequests()) {
            String result = new DefaultToolExecutor(tools, request).execute(request, null);
            messages.add(ToolExecutionResultMessage.from(request, result));   // 内含 request 的 id
        }
        // —— 回边：回到循环开头，让模型带着工具结果再想 ——
    }
}

模型偷懒了怎么办

问 "Suggest two Cornwall beach towns with nice weather"（推荐两个天气好的康沃尔海滨小镇）。 理想的过程是：先用搜索工具找海滨小镇，再逐个查天气。但实际上，模型常常跳过搜索，直接凭自己的记忆报出两个镇名去查天气 —— 答案看着没毛病，却绕开了你的知识库。

解决办法是加一条系统消息，明确规定「需要的信息只能从工具获取」：

SYSTEM_MESSAGE = SystemMessage(content="""You are a helpful assistant
that can search travel information and get the weather forecast.
Only use the tools to find the information you need (including town names).""")

ⓘ 与仓库代码的一处差别

仓库的 main_02_02.py 是把系统消息 append 到 state["messages"] 这个列表的末尾。 这样做有两个副作用：直接修改了状态对象；循环每转一圈就多追加一条。 上面改成「新建列表、系统消息放最前」，是更常见也更稳妥的写法。

当前的标准写法：create_agent 与中间件

仓库基于 LangGraph 1.0 的 create_react_agent。在 LangChain 1.x 里，官方推荐的入口已经换成 langchain.agents.create_agent（TypeScript 是 langchain 包的 createAgent）。 循环还是同一个循环，但多了一个重要的扩展机制：中间件（middleware）。

如果你写过 Web 后端，这个词不陌生：请求进来和响应出去的路上，可以插入一层层处理逻辑。 智能体的中间件同理 —— 在 ReAct 循环的几个固定位置留了「插槽」，你可以在不改图结构的前提下加进自己的逻辑：

自己写一个

内置的不够用时，自定义中间件也只是一个函数。下面两个例子各对应一类插槽：

from typing import Any, Callable
from langchain.agents.middleware import before_model, wrap_tool_call, AgentState
from langchain.messages import AIMessage, ToolMessage
from langchain.tools.tool_node import ToolCallRequest
from langgraph.runtime import Runtime
from langgraph.types import Command

# —— 「之前 / 之后」型：读状态，返回更新；可以直接跳到结束 ——
@before_model(can_jump_to=["end"])
def check_message_limit(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    if len(state["messages"]) >= 50:
        return {"messages": [AIMessage("Conversation limit reached.")],
                "jump_to": "end"}                 # 不再调用模型，直接结束
    return None                                   # 返回 None = 什么都不改，继续

# —— 「包裹」型：拿到请求和「真正干活的函数」，自己决定怎么调 ——
@wrap_tool_call
def monitor_tool(
    request: ToolCallRequest,
    handler: Callable[[ToolCallRequest], ToolMessage | Command],
) -> ToolMessage | Command:
    print(f"Executing tool: {request.tool_call['name']}  args: {request.tool_call['args']}")
    result = handler(request)                     # 调用真正的工具
    print("Tool completed successfully")
    return result

agent = create_agent(
    model="openai:gpt-4.1-mini",
    tools=[search_travel_info, weather_forecast],
    middleware=[check_message_limit, monitor_tool],
)

const messageLimitMiddleware = createMiddleware({
  name: "MessageLimitMiddleware",

    canJumpTo: ["end"],

      if (state.messages.length >= 50) {
        return { messages: [new AIMessage("Conversation limit reached.")],
                 jumpTo: "end" };               // 不再调用模型，直接结束
      }
      return;                                   // 什么都不改，继续
    },
  },
});

  },

以前想在循环里加一步（比如审批），得放弃预置智能体、自己手写整张图。现在多数定制只需要往列表里加一个中间件。 本章前面手写的图仍然值得学 —— 它告诉你中间件挂在什么上面；但真正动手时，先看有没有现成的中间件能用。 顺带一提：第 14 章用到的 pre_model_hook，在新写法里对应的就是 before_model 中间件。

⚠ 智能体的三个常见失控方式
  • 不用工具：直接凭记忆回答。→ 写清工具描述，用系统消息约束。
  • 停不下来：反复调用同一个工具。→ 设置最大步数（LangGraph 的 recursion_limit，或上面的 remaining_steps）。
  • 参数填错：比如把整句话当成镇名。→ 给参数加描述和类型约束；工具内部做校验，出错时返回清晰的错误信息，模型通常会自己纠正并重试。

小结

  • 工具调用是一个协议：模型输出「我想调用某函数 + 参数」，你的程序执行后把结果发回。模型本身不执行任何东西。
  • 工具 = 函数 + 说明书（名称、描述、参数格式）。描述的质量直接决定模型用得对不对。
  • ReAct：思考 → 行动 → 观察，循环到模型认为可以回答为止。
  • 最小的智能体图：llm_node ⇄ tools，由 tools_condition 判断最后一条消息有没有 tool_calls。
  • 状态是一个只追加的消息列表（reducer）。四种消息：Human、AI（可带 tool_calls）、Tool、System。
  • 加工具只需往列表里添一项；用系统消息引导模型「只用工具获取信息」，可以减少幻觉。
  • create_react_agent（Java 里是带 tools 的 AI Service）把这一切打包成几行代码。
  • 当前的标准入口是 create_agent；中间件在循环的六个固定位置插入逻辑，限流、重试、摘要、人工审批等都有内置实现。
