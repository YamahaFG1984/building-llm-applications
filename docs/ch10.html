第 10 章

查询生成、路由与检索后处理

到目前为止，「检索」一直等于「去向量库里做相似度搜索」。但真实世界的数据不只躺在向量库里： 酒店价格在关系数据库里，人物关系在图数据库里。这一章把 RAG 的检索环节打开： 让 LLM 为不同的数据源生成对应的查询语句、决定该去哪个数据源，并在检索之后再筛一遍结果。

本章目标

  • 用「自查询」从问题里自动提取元数据过滤条件
  • 让 LLM 把自然语言翻译成 SQL，并安全地执行
  • 了解语义 SQL 和知识图谱 RAG 的思路
  • 搭一个路由器，把问题分发到合适的数据源
  • 用 RAG Fusion（倒数排名融合）对多路检索结果重新排序

本章地图

自查询：把问题里的条件变成过滤器

用户问：「英国小镇纽基（Newquay）有什么节日活动？」纯语义检索可能把布莱顿的节日也找回来，因为「节日活动」的意思太像了。 但如果每个文本块都带着 destination 元数据，我们就可以先按元数据精确过滤，再做语义搜索。

入库时带上元数据

过滤的前提是数据里有可过滤的字段。入库时给每个文档加上 destination 和 region；切块后，每个块会继承这些元数据。

import dev.langchain4j.model.output.structured.Description;
import dev.langchain4j.store.embedding.filter.Filter;

record DestinationSearch(
        @Description("Similarity search query applied to tourist destinations.") String contentSearch,
        @Description("The specific UK destination to be searched, or null.") String destination,
        @Description("The name of the UK region to be searched, or null.") String region) {}

interface QueryGenerator {
    @SystemMessage("""
            You are an expert at converting user questions into vector database queries.
            You have access to a database of tourist destinations.
            Given a question, return a database query optimized to retrieve the most relevant results.
            If there are acronyms or words you are not familiar with, do not try to rephrase them.""")
    DestinationSearch generate(String question);
}

static Filter buildFilter(DestinationSearch s) {
    Filter filter = null;
    if (s.destination() != null && !s.destination().isBlank())
        filter = metadataKey("destination").isEqualTo(s.destination());
    if (s.region() != null && !s.region().isBlank()) {
        Filter byRegion = metadataKey("region").isEqualTo(s.region());
        filter = (filter == null) ? byRegion : filter.and(byRegion);
    }
    return filter;
}

var generator = AiServices.create(QueryGenerator.class, llm);
DestinationSearch q = generator.generate(
        "Tell me about events or festivals in the UK town of Newquay");

var request = EmbeddingSearchRequest.builder()
        .queryEmbedding(embeddingModel.embed(q.contentSearch()).content())
        .filter(buildFilter(q))
        .maxResults(3).build();
store.search(request).matches().forEach(m -> System.out.println(m.embedded().text()));
⚠ 过滤是精确匹配，一个字母都不能差

模型可能输出 "St Ives"，而库里存的是 "St_Ives" —— 结果就是一条都查不到。 常见的对策：在字段描述里列出所有合法取值（或用枚举类型约束输出）； 入库和查询时对取值做同样的规范化；过滤后结果为空时，退回到不带过滤的普通检索。

Text-to-SQL：让 LLM 写 SQL

「卡迪夫有哪些住宿优惠？」这种问题的答案在关系数据库里，语义搜索帮不上忙，需要的是一条精确的 SQL。 示例数据库 UkBooking 有四张表（建表脚本在 ch10/CreateUkBooking.sql）：

流程分三步：把表结构告诉模型 → 模型生成 SQL → 执行 SQL 拿结果。

  "SELECT sql FROM sqlite_master WHERE type = 'table' AND sql IS NOT NULL").all() as { sql: string }[])
  .map((r) => r.sql).join("\n\n");

const sqlLlm = new ChatOpenAI({ model: "gpt-4.1" });           // SQL 生成用更强的模型

const sqlGenChain = ChatPromptTemplate.fromTemplate(`
You are a SQLite expert. Given the database schema below, write one syntactically correct
SQLite SELECT query that answers the question. Always prefix column names with the table
name. Return at most 5 rows unless told otherwise.

Schema:
{schema}

Question: {question}`)
  .pipe(sqlLlm.withStructuredOutput(z.object({
    sql: z.string().describe("A single executable SQLite SELECT statement"),
  })));

async function sqlRetriever(question: string): Promise<string> {
  const { sql } = await sqlGenChain.invoke({ schema, question });      // ① 生成
  if (!/^\s*select\b/i.test(sql)) throw new Error("Only SELECT is allowed");   // ② 把关
  return JSON.stringify(db.prepare(sql).all());                        // ③ 执行
}

// 依赖：org.xerial:sqlite-jdbc
import java.sql.*;

record SqlQuery(@Description("A single executable SQLite SELECT statement") String sql) {}

interface SqlGenerator {
    @UserMessage("""
            You are a SQLite expert. Given the database schema below, write one syntactically
            correct SQLite SELECT query that answers the question. Always prefix column names
            with the table name. Return at most 5 rows unless told otherwise.

            Schema:
            {{schema}}

            Question: {{question}}""")
    SqlQuery generate(@V("schema") String schema, @V("question") String question);
}

static String sqlRetriever(SqlGenerator generator, String question) throws SQLException {
    // 以只读方式打开数据库
    try (Connection conn = DriverManager.getConnection("jdbc:sqlite:file:UkBooking.db?mode=ro")) {

        var schema = new StringBuilder();                      // 读出所有建表语句
        try (var rs = conn.createStatement().executeQuery(
                "SELECT sql FROM sqlite_master WHERE type = 'table' AND sql IS NOT NULL")) {
            while (rs.next()) schema.append(rs.getString(1)).append("\n\n");
        }

        String sql = generator.generate(schema.toString(), question).sql();        // ① 生成
        if (!sql.trim().toLowerCase().startsWith("select"))                        // ② 把关
            throw new IllegalArgumentException("Only SELECT is allowed");

        var rows = new StringBuilder();                                            // ③ 执行
        try (var rs = conn.createStatement().executeQuery(sql)) {
            int cols = rs.getMetaData().getColumnCount();
            while (rs.next()) {
                for (int i = 1; i <= cols; i++) rows.append(rs.getString(i)).append(i < cols ? " | " : "\n");
            }
        }
        return rows.toString();
    }
}
⚠ 执行模型生成的 SQL，等于让陌生人操作你的数据库
  • 用只读账号 / 只读连接。这是最重要的一条：即使模型（或被恶意提示词操纵的模型）写出 DROP TABLE，也执行不了。
  • 只暴露需要的表和列，不要把含有敏感信息的表结构交给模型。
  • 限制返回行数和执行时间，防止一条慢查询拖垮数据库。
  • 上面代码里「以 SELECT 开头」的检查只是聊胜于无的辅助手段，不能代替数据库层面的权限控制。

语义 SQL：在关系数据库里做模糊匹配

普通 SQL 的 WHERE first_name = 'Roberto' 只能精确匹配，LIKE 'Rob%' 也只能匹配前缀，找不到 Bob 或 Bert。 PostgreSQL 的 pgvector 扩展让你给某一列存一份向量，从而在 SQL 里按语义距离排序： 

-- 1. 给要做语义搜索的字段加一个向量列
ALTER TABLE users ADD COLUMN first_name_embedding VECTOR(1536);

-- 2.（在应用代码里）计算每个 first_name 的向量并 UPDATE 进去

-- 3. 查询：把 'Roberto' 的向量作为参数传入，按距离从近到远排序
SELECT first_name
FROM users
WHERE first_name_embedding IS NOT NULL
ORDER BY first_name_embedding <-> $1        -- <-> 是 pgvector 的距离运算符
LIMIT 10;

它的威力在于把精确条件和语义条件写在同一条 SQL 里，还能跨表 JOIN： 「价格低于 100 英镑（精确）、描述里有『海景』的意思（语义）的酒店」。 和 Text-to-SQL 结合的方式也一样：在提示词里告诉模型哪些列有向量、距离运算符怎么用，让它生成这种查询。

图数据库与知识图谱 RAG

有些知识的核心是关系：谁是谁的上级、哪个零件属于哪个部件、哪种药和哪种药不能同服。 这类数据用图数据库表示最自然：节点是实体，边是关系。

LLM 让图数据库好用了很多，它在三个环节都能出力，合起来就是知识图谱 RAG（KG-RAG）：

  1. 抽取从非结构化文本里抽取实体和关系，构建图谱。
  2. 生成查询把自然语言问题翻译成 Cypher（Neo4j）或 SPARQL。和 Text-to-SQL 同理，需要少样本示例和较强的模型。
  3. 生成答案把「问题 + 查询语句 + 查询结果」交给模型，转成自然语言回答。这一步用便宜的小模型就够了。
问题：Roberto 支持的球队在哪个联赛踢球？

生成的 Cypher：
  MATCH (p:Person {name: "Roberto"})-[:isFanOf]->(t:SoccerTeam)-[:playsIn]->(l:SoccerLeague)
  RETURN l.name

查询结果：SerieA
最终回答：Roberto 支持的国际米兰在意甲联赛踢球。

向量检索擅长「找相似的片段」，图谱擅长「沿着关系多跳推理」并且可以解释（查询路径一目了然）。两者经常搭配使用。

路由：这个问题该去哪儿查

现在有了两个数据源：向量库（旅游介绍）和关系数据库（住宿优惠）。 用户的问题该交给谁？让 LLM 当「分诊台」： 

from typing import Literal
from pydantic import BaseModel, Field
from langchain_core.runnables import RunnableLambda, RunnablePassthrough

# —— 路由器：用 Literal 把输出限定为两个合法值之一 ——
class RouteQuery(BaseModel):
    """Route a user question to the most relevant datasource."""
    datasource: Literal["tourist_info_store", "uk_booking_db"] = Field(
        ..., description="Given a user question, route it either to a tourist info "
                         "vector store or a UK accommodation booking relational database.")

route_prompt = ChatPromptTemplate.from_messages([
    ("system", """You are an expert at routing a user question to a tourist info vector store
or to an UK accommodation booking relational database.
The vector store contains tourist information about UK destinations.
Use the vectorstore for general tourist information questions on UK destinations.
For questions about accommodation availability or booking, use the UK Booking database."""),
    ("human", "{question}"),
])

    'tourist_info_store': tourist_info_retriever_chain,

    return retriever_chains[selected.datasource]

# —— 完整的 RAG：先选检索器，再走标准流程 ——
rag_prompt = ChatPromptTemplate.from_template("""
Given a question and some context, answer the question.
If you get a structured context, like a tuple, try to infer the meaning of the components:
typically they refer to accommodation offers, and the number is a percentage (0.2 means 20%).
If you do not know the answer, just say I do not know.

Context: {context}
Question: {question}
""")

def execute_rag_chain(question):
    chosen_retriever = retriever_chooser(question)
    full_rag_chain = (
        {"context": {"question": RunnablePassthrough()} | chosen_retriever,
         "question": RunnablePassthrough()}
        | rag_prompt | llm | StrOutputParser())
    return full_rag_chain.invoke(question)

print(execute_rag_chain("Give me some offers for Cardiff, including the accommodation name"))
print(execute_rag_chain("Tell me about events or festivals in the UK town of Newquay"))

RAG Fusion：倒数排名融合

第 9 章的多查询把几路检索结果简单地合并去重。但哪些该排在前面？ 倒数排名融合（Reciprocal Rank Fusion，RRF）的想法很朴素： 一个文档如果在多路检索里都排名靠前，它就更可能真的相关。 

def reciprocal_rank_fusion(results_groups: list[list], k=60):
    """融合多组有序的检索结果。同一个文档在各组里的得分累加。"""
    fused_scores, doc_by_key = {}, {}

    for results_group in results_groups:
        for rank, doc in enumerate(results_group):
            key = doc.page_content                       # 用内容识别「同一个文档」
            doc_by_key[key] = doc
            fused_scores[key] = fused_scores.get(key, 0) + 1 / (rank + 1 + k)

    reranked = sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)
    return [(doc_by_key[key], score) for key, score in reranked]

    return [doc for doc, score in reranked[:3]]

/** 融合多组有序的检索结果。同一个文档在各组里的得分累加。 */
function reciprocalRankFusion(resultsGroups: Document[][], k = 60): [Document, number][] {
  const fusedScores = new Map<string, number>();
  const docByKey = new Map<string, Document>();

  for (const group of resultsGroups) {
    group.forEach((doc, rank) => {
      const key = doc.pageContent;                      // 用内容识别「同一个文档」
      docByKey.set(key, doc);
      fusedScores.set(key, (fusedScores.get(key) ?? 0) + 1 / (rank + 1 + k));
    });
  }
  return [...fusedScores.entries()]
    .sort((a, b) => b[1] - a[1])
    .map(([key, score]) => [docByKey.get(key)!, score]);
}

const retriever = ukWithMetadataCollection.asRetriever({ k: 3 });

/** 融合多组有序的检索结果。同一个文档在各组里的得分累加。 */
static List<String> reciprocalRankFusion(List<List<String>> resultsGroups, int k, int topN) {
    Map<String, Double> fusedScores = new HashMap<>();

    for (List<String> group : resultsGroups) {
        for (int rank = 0; rank < group.size(); rank++) {
            fusedScores.merge(group.get(rank), 1.0 / (rank + 1 + k), Double::sum);
        }
    }
    return fusedScores.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .limit(topN)
            .map(Map.Entry::getKey)
            .toList();
}

ⓘ 与仓库 Notebook 的一处差别

仓库里的 reciprocal_rank_fusion 用 (组号, 组内排名) 作为字典的键，这样每条结果的键都是唯一的， 同一个文档在不同组里的得分不会累加 —— 实际效果只是按组内排名排序。 上面的版本改用文档内容作为键，才是 RRF 的本意：跨组累加。读 Notebook 时可以对照着看。

💡 RRF 最常见的用途：混合检索

因为 RRF 只看排名、不看分数，它特别适合融合不同类型的检索结果 —— 比如向量检索（擅长语义）和关键词检索 BM25（擅长专有名词、型号、代码）。这种「混合检索」在生产系统里非常普遍。

小结

  • 自查询：让 LLM 从问题里提取元数据过滤条件，先精确过滤再语义搜索。前提是入库时带上了元数据。
  • Text-to-SQL：把表结构给模型 → 生成 SQL → 执行。务必使用只读连接，权限控制放在数据库层面。
  • 语义 SQL（pgvector）把精确条件和语义条件写在一条查询里；知识图谱 RAG 擅长多跳关系推理。
  • 路由：用结构化输出（枚举 / Literal）让 LLM 在预设的数据源里选一个。
  • 检索后处理：相似度阈值、关键词过滤、时间加权、重排，以及 RAG Fusion。
  • RRF 只看排名：得分 = Σ 1 / (k + 排名)，在多路结果里都靠前的文档胜出。
  • 至此，第 8 章开头列的六类问题都有了对应的工具。
