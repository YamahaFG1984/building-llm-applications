💡 Notebook 的三个使用习惯
  • 按顺序逐格执行（Shift + Enter）。后面的单元格依赖前面定义的变量，跳着执行会报「变量未定义」。
  • 改了前面的单元格后，记得重新运行它以及之后依赖它的单元格。
  • 状态乱了就 Kernel → Restart & Run All，从头来一遍。

如何选择 LLM（附录 C）

选模型不是比谁的排行榜分数高，而是一连串的取舍。可以按这个顺序问自己：

比较模型时看哪些维度

维度含义为什么重要
准确度在标准测试集上的得分参考价值有限：务必用你自己的任务再测一遍
上下文窗口一次能处理多少 token决定能塞进多少资料和对话历史
速度首个 token 延迟、每秒生成 token 数交互式应用对延迟很敏感
价格每百万输入 / 输出 token 的费用输出通常比输入贵数倍
模态是否支持图片、音频输入多模态 RAG（第 8 章）需要
工具调用是否支持、是否稳定智能体（第 11 章起）的前提
结构化输出能否可靠地按 schema 返回 JSON路由、自查询、护栏都依赖它
多语言对中文及其他语言的支持不同模型差距很大
许可闭源 API 还是开源权重，开源许可是否允许商用影响部署方式和合规

⚠ 别太迷信排行榜

模型更新极快，书里和这里列出的具体型号与分数都会很快过时；公开基准也存在「题目泄露进训练数据」的问题。 可靠的做法是：先用最便宜的模型跑通，建立一小套属于自己业务的测试题（第 14 章的「评估」）， 效果不够时再逐级换更强的模型，用数据说话。因为 LangChain 统一了接口，换模型通常只改一行。

在本地运行开源 LLM（附录 E）

不想付费、不想让数据离开自己的电脑，或者只是好奇？可以在本机跑开源模型。

为什么可行：量化

原始模型的每个参数是 16 或 32 位浮点数，一个 70 亿参数的模型要占十几 GB 显存。 量化（quantization）把参数压缩成 4 位或 8 位整数，体积缩小到原来的四分之一左右，精度只损失一点点 —— 于是普通笔记本的内存和 CPU 也能跑起来。常见的量化模型文件格式是 GGUF。

from openai import OpenAI
from langchain_openai import ChatOpenAI

LOCAL_BASE_URL = "http://localhost:11434/v1"       # Ollama；LM Studio 默认是 1234 端口

# —— 方式一：OpenAI 官方客户端，只改 base_url ——
client = OpenAI(base_url=LOCAL_BASE_URL, api_key="NO_KEY_NEEDED")

completion = client.chat.completions.create(
    model="mistral",
    messages=[
        {"role": "system", "content": "You are a helpful AI assistant."},
        {"role": "user", "content": "How many Greek temples are there in Paestum?"}],
    temperature=0.7)
print(completion.choices[0].message.content)

# —— 方式二：LangChain ——
llm = ChatOpenAI(base_url=LOCAL_BASE_URL, api_key="NO_KEY_NEEDED", model="mistral")
print(llm.invoke("How many Greek temples are there in Paestum?").content)

让整个项目可切换

还记得第 4 章把「创建模型」集中在 get_llm() 一个函数里吗？这个设计现在见效了 —— 只改这一个函数，整个研究摘要引擎就跑在本地模型上： 

import os
from langchain_openai import ChatOpenAI

def get_llm():
    if os.getenv("USE_LOCAL_LLM") == "true":
        return ChatOpenAI(
            base_url=os.getenv("LOCAL_LLM_URL", "http://localhost:11434/v1"),
            api_key="NO_KEY_NEEDED",
            model=os.getenv("LOCAL_LLM_MODEL", "mistral"))
    return ChatOpenAI(model="gpt-5-nano")       # 默认：OpenAI

import { ChatOpenAI } from "@langchain/openai";

export function getLlm() {
  if (process.env.USE_LOCAL_LLM === "true") {
    return new ChatOpenAI({
      model: process.env.LOCAL_LLM_MODEL ?? "mistral",
      apiKey: "NO_KEY_NEEDED",
      configuration: { baseURL: process.env.LOCAL_LLM_URL ?? "http://localhost:11434/v1" },
    });
  }
  return new ChatOpenAI({ model: "gpt-5-nano" });   // 默认：OpenAI
}

public class LlmModels {
    public static ChatModel getLlm() {
        if ("true".equals(System.getenv("USE_LOCAL_LLM"))) {
            return OpenAiChatModel.builder()
                    .baseUrl(env("LOCAL_LLM_URL", "http://localhost:11434/v1"))
                    .apiKey("NO_KEY_NEEDED")
                    .modelName(env("LOCAL_LLM_MODEL", "mistral"))
                    .build();
        }
        return OpenAiChatModel.builder()            // 默认：OpenAI
                .apiKey(System.getenv("OPENAI_API_KEY")).modelName("gpt-5-nano").build();
    }

    private static String env(String key, String fallback) {
        String v = System.getenv(key);
        return v != null ? v : fallback;
    }
}

本地模型的现实

云端 API本地开源模型
费用按 token 计费免费（电费和硬件除外）
隐私数据发往第三方数据不离开本机
速度快没有 GPU 时明显慢，长文本尤甚
效果通常更强摘要、问答够用；复杂推理有差距
工具调用 / 结构化输出稳定视模型而定，小模型常常不可靠
离线可用否是
⚠ 用本地模型做智能体章节要留意

第 1–10 章的示例换成本地模型基本都能跑通。但第 11 章起的智能体强依赖工具调用和结构化输出， 而不少小型开源模型在这两项上并不稳定 —— 表现为不调用工具、参数格式错误、或输出无法解析的 JSON。 做这些章节的练习时，请选择明确标注支持 tool calling 的模型，并做好它偶尔出错的准备。 另外，嵌入模型也需要一并替换成本地的（例如通过 Ollama 运行的嵌入模型），否则向量化这一步仍然会调用 OpenAI。
