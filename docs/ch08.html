第 8 章

高级索引

基础 RAG 跑起来很容易，但很快会撞墙：明明资料里有答案，就是检索不出来；或者检索出来了，却只有半句话，模型看不明白。 从这一章起的三章，是一个「RAG 效果不好怎么办」的工具箱。先从源头下手：文档到底该怎么切、怎么建索引。

本章目标

  • 知道基础 RAG 常见的六类问题，以及各自对应的解法
  • 理解块大小的两难：小块好找，大块好懂
  • 按文档结构（HTML 标题）和按大小两种方式切分
  • 掌握「用小的去找，把大的交出去」这个核心套路的四种变体
  • 了解表格和图片这类非纯文本内容怎么处理

切分策略

策略优点缺点LangChain 的类
按文档结构（标题层级）每块是一个完整的小主题，语义最准块大小差别很大HTMLHeaderTextSplitter、HTMLSectionSplitter、MarkdownHeaderTextSplitter
按 token 数大小一致，方便控制成本边界处会切断句子TokenTextSplitter
按字符数大小一致，实现最简单切断句子，损失语义CharacterTextSplitter
按段落 / 句子 / 单词递归多数情况下保住语义小块可能缺上下文RecursiveCharacterTextSplitter

实验：同一个网页，两种切法

数据换成英国旅游目的地。以 Wikivoyage 的 Cornwall（康沃尔）页面为例，建两个集合：一个按 HTML 标题切成细块，一个按 3000 字符切成粗块。 对应仓库的 ch08/08-advanced_indexing.ipynb。 

from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain_community.document_loaders import AsyncHtmlLoader
from langchain_community.document_transformers import Html2TextTransformer
from langchain_text_splitters import HTMLSectionSplitter, RecursiveCharacterTextSplitter

embeddings = OpenAIEmbeddings(openai_api_key=OPENAI_API_KEY)
cornwall_granular_collection = Chroma(collection_name="cornwall_granular",
                                      embedding_function=embeddings)
cornwall_coarse_collection = Chroma(collection_name="cornwall_coarse",
                                    embedding_function=embeddings)

docs = AsyncHtmlLoader("https://en.wikivoyage.org/wiki/Cornwall").load()

# 细块：每个 h1 / h2 小节一块
html_section_splitter = HTMLSectionSplitter(
    headers_to_split_on=[("h1", "Header 1"), ("h2", "Header 2")])

def split_docs_into_granular_chunks(docs):
    all_chunks = []
    for doc in docs:
        all_chunks.extend(html_section_splitter.split_text(doc.page_content))
    return all_chunks

# 粗块：先把 HTML 转成纯文本，再按 3000 字符切
html2text_transformer = Html2TextTransformer()
text_splitter = RecursiveCharacterTextSplitter(chunk_size=3000, chunk_overlap=300)

def split_docs_into_coarse_chunks(docs):
    text_docs = html2text_transformer.transform_documents(docs)
    return text_splitter.split_documents(text_docs)

cornwall_granular_collection.add_documents(split_docs_into_granular_chunks(docs))
cornwall_coarse_collection.add_documents(split_docs_into_coarse_chunks(docs))

# 同一个问题，分别查两个集合
query = "Events or festivals in Cornwall"
for doc in cornwall_granular_collection.similarity_search(query, k=3): print(doc)
for doc in cornwall_coarse_collection.similarity_search(query, k=3): print(doc)

// LangChain.js 没有 HTMLSectionSplitter，用 cheerio 自己按 h2 切，逻辑很直白。
import * as cheerio from "cheerio";
import { Document } from "@langchain/core/documents";
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import { Chroma } from "@langchain/community/vectorstores/chroma";
import { OpenAIEmbeddings } from "@langchain/openai";

const embeddings = new OpenAIEmbeddings();
const granular = new Chroma(embeddings, { collectionName: "cornwall_granular" });
const coarse   = new Chroma(embeddings, { collectionName: "cornwall_coarse" });

const url = "https://en.wikivoyage.org/wiki/Cornwall";
const html = await (await fetch(url)).text();

// 细块：每个 h2 小节一块
function splitIntoGranularChunks(html: string, source: string): Document[] {
  const $ = cheerio.load(html);
  const chunks: Document[] = [];
  $("h2").each((_, h2) => {
    const title = $(h2).text().trim();
    // 从这个 h2 往后，直到下一个 h2 之前的所有兄弟节点
    const text = $(h2).closest(".mw-heading, h2").nextUntil(".mw-heading2, h2").text().trim();
    if (text) chunks.push(new Document({
      pageContent: `${title}\n${text}`, metadata: { source, "Header 2": title } }));
  });
  return chunks;
}

// 粗块：去标签后按 3000 字符切
async function splitIntoCoarseChunks(html: string, source: string): Promise<Document[]> {
  const $ = cheerio.load(html);
  $("script, style").remove();
  const splitter = new RecursiveCharacterTextSplitter({ chunkSize: 3000, chunkOverlap: 300 });
  return splitter.createDocuments([$("body").text()], [{ source }]);
}

await granular.addDocuments(splitIntoGranularChunks(html, url));
await coarse.addDocuments(await splitIntoCoarseChunks(html, url));

const query = "Events or festivals in Cornwall";
console.log(await granular.similaritySearch(query, 3));
console.log(await coarse.similaritySearch(query, 3));

// 用 Jsoup 按 h2 切细块；粗块用 LangChain4j 的递归切分器。
import org.jsoup.Jsoup;
import org.jsoup.nodes.Element;

String url = "https://en.wikivoyage.org/wiki/Cornwall";
var page = Jsoup.connect(url).get();

// 细块：每个 h2 小节一块
List<TextSegment> granularChunks = new ArrayList<>();
for (Element h2 : page.select("h2")) {
    var text = new StringBuilder(h2.text()).append("\n");
    Element start = h2.parent().hasClass("mw-heading") ? h2.parent() : h2;
    for (Element sib = start.nextElementSibling();
         sib != null && sib.selectFirst("h2") == null && !sib.tagName().equals("h2");
         sib = sib.nextElementSibling()) {
        text.append(sib.text()).append("\n");
    }
    granularChunks.add(TextSegment.from(text.toString(),
            Metadata.from(Map.of("source", url, "header2", h2.text()))));
}

// 粗块：纯文本按 3000 字符切，重叠 300
List<TextSegment> coarseChunks = DocumentSplitters.recursive(3000, 300)
        .split(Document.from(page.body().text(), Metadata.from("source", url)));

granularStore.addAll(embeddingModel.embedAll(granularChunks).content(), granularChunks);
coarseStore.addAll(embeddingModel.embedAll(coarseChunks).content(), coarseChunks);

实验结论和图 8-2 一致：细块检索命中的小节很精准，但有的块只有寥寥几行；粗块内容丰富，但混进了不少无关话题。

💡 没有通用的最佳块大小

它取决于文档类型（合同条款 vs 游记）、问题类型（查事实 vs 要综述）和嵌入模型。 唯一可靠的办法是：准备一批有代表性的问题，换几种切法，实测哪种检索得最准。

核心套路：用小的去找，把大的交出去

既然「好找」和「好懂」矛盾，那就把这两件事拆开： 向量库里存用来匹配的小东西，另外用一个文档库存用来阅读的大块，两者靠 ID 关联。

变体向量库里存的「代理」返回给模型的入库成本
① 父子块把粗块再切成的小块粗块低（不调 LLM）
② 摘要嵌入LLM 为粗块写的摘要粗块高（每块调一次 LLM）
③ 假设问题嵌入LLM 设想的「这块能回答哪些问题」粗块高
④ 细块扩展细块本身细块 + 前后相邻的块低

变体 ①：父子块（ParentDocumentRetriever）

LangChain 为最常见的这种情况提供了现成的类，自动完成「粗块切子块、建立关联、检索时换回父块」：

from langchain_classic.retrievers import ParentDocumentRetriever
from langchain_classic.storage import InMemoryStore

parent_splitter = RecursiveCharacterTextSplitter(chunk_size=3000)   # 父块：给模型读
child_splitter = RecursiveCharacterTextSplitter(chunk_size=500)     # 子块：用来匹配

child_chunks_collection = Chroma(collection_name="uk_child_chunks",
                                 embedding_function=embeddings)
doc_store = InMemoryStore()                                         # 存父块

parent_doc_retriever = ParentDocumentRetriever(
    vectorstore=child_chunks_collection,
    docstore=doc_store,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter)

for destination_url in uk_destination_urls:
    html_docs = AsyncHtmlLoader(destination_url).load()
    text_docs = html2text_transformer.transform_documents(html_docs)
    parent_doc_retriever.add_documents(text_docs, ids=None)   # 一次完成两边的入库

# 检索：匹配的是子块，返回的是父块
retrieved_docs = parent_doc_retriever.invoke("Cornwall Ranger")
print(len(retrieved_docs[0].page_content))        # ≈ 3000

# 对比：直接搜子块，只能拿到 500 字符的碎片
child_docs_only = child_chunks_collection.similarity_search("Cornwall Ranger")
print(len(child_docs_only[0].page_content))       # ≈ 500

// LangChain4j 没有 ParentDocumentRetriever，手写一个小工具类。
// 它同样适用于后面的摘要、假设问题、细块扩展 —— 区别只在「代理文本从哪来」。
class MultiVectorIndex {
    private final EmbeddingStore<TextSegment> vectorStore;     // 存代理
    private final EmbeddingModel embeddingModel;
    private final Map<String, String> docStore = new ConcurrentHashMap<>();   // doc_id → 父块

    MultiVectorIndex(EmbeddingStore<TextSegment> vectorStore, EmbeddingModel embeddingModel) {
        this.vectorStore = vectorStore;
        this.embeddingModel = embeddingModel;
    }

    /** 存入一个父块，以及指向它的若干代理文本 */
    void add(String parentText, List<String> proxies) {
        String docId = UUID.randomUUID().toString();
        docStore.put(docId, parentText);
        List<TextSegment> segments = proxies.stream()
                .map(p -> TextSegment.from(p, Metadata.from("doc_id", docId)))
                .toList();
        vectorStore.addAll(embeddingModel.embedAll(segments).content(), segments);
    }

    /** 匹配代理，返回去重后的父块 */
    List<String> retrieve(String query, int k) {
        var request = EmbeddingSearchRequest.builder()
                .queryEmbedding(embeddingModel.embed(query).content())
                .maxResults(k).build();
        return vectorStore.search(request).matches().stream()
                .map(m -> m.embedded().metadata().getString("doc_id"))
                .distinct()
                .map(docStore::get)
                .toList();
    }
}

// —— 变体 ①：代理 = 父块切出来的子块 ——
var index = new MultiVectorIndex(childChunksStore, embeddingModel);
var parentSplitter = DocumentSplitters.recursive(3000, 0);
var childSplitter  = DocumentSplitters.recursive(500, 0);

for (String url : ukDestinationUrls) {
    for (TextSegment parent : parentSplitter.split(loadAsTextDoc(url))) {
        List<String> children = childSplitter.split(Document.from(parent.text())).stream()
                .map(TextSegment::text).toList();
        index.add(parent.text(), children);
    }
}

System.out.println(index.retrieve("Cornwall Ranger", 4).get(0).length());   // ≈ 3000

"Cornwall Ranger" 是一种火车通票的名字。只搜子块能找到提到它的那句话，却丢掉了周围关于「在康沃尔怎么出行」的上下文； 父子块检索既找得准，又把完整的一段交给了模型。

变体 ②③：用摘要或假设问题做代理（MultiVectorRetriever）

更一般的工具是 MultiVectorRetriever：它不管代理从哪来，只要求每个代理的元数据里带着父块的 doc_id。 于是代理可以是任何东西 —— 包括让 LLM 生成的文本。

② 摘要嵌入

让 LLM 为每个粗块写一段摘要，嵌入摘要。摘要去掉了细枝末节，向量更能代表这块「主要讲什么」。 适合「概括性」的问题，比如「康沃尔的交通情况怎么样」。

③ 假设问题嵌入

让 LLM 为每个粗块设想几个「它能回答的问题」，嵌入这些问题。 这样检索时是问题对问题匹配，比「问题对陈述」更容易对上。

import uuid
from typing import List
from pydantic import BaseModel, Field
from langchain_classic.retrievers.multi_vector import MultiVectorRetriever
from langchain_classic.storage import InMemoryByteStore
from langchain_core.documents import Document
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

llm = ChatOpenAI(model="gpt-5-nano", openai_api_key=OPENAI_API_KEY)
doc_key = "doc_id"

# —— ② 生成摘要的链 ——
summarization_chain = (
    {"document": lambda x: x.page_content}
    | ChatPromptTemplate.from_template("Summarize the following document:\n\n{document}")
    | llm
    | StrOutputParser())

# —— ③ 生成假设问题的链：用结构化输出直接拿到字符串列表 ——
class HypotheticalQuestions(BaseModel):
    """A list of hypothetical questions for given text."""
    questions: List[str] = Field(..., description="List of hypothetical questions for given text")

hypothetical_questions_chain = (
    {"document_text": lambda x: x.page_content}
    | ChatPromptTemplate.from_template(
        "Generate a list of exactly 4 hypothetical questions that the below text "
        "could be used to answer:\n\n{document_text}")
    | llm.with_structured_output(HypotheticalQuestions)
    | (lambda x: x.questions))

# —— 通用的入库流程：只有「代理怎么来」这一行不同 ——
def build_retriever(collection_name, make_proxies):
    retriever = MultiVectorRetriever(
        vectorstore=Chroma(collection_name=collection_name, embedding_function=embeddings),
        byte_store=InMemoryByteStore())

    for destination_url in uk_destination_urls:
        html_docs = AsyncHtmlLoader(destination_url).load()
        text_docs = html2text_transformer.transform_documents(html_docs)
        coarse_chunks = parent_splitter.split_documents(text_docs)
        coarse_chunks_ids = [str(uuid.uuid4()) for _ in coarse_chunks]

        proxies = []
        for coarse_chunk, coarse_chunk_id in zip(coarse_chunks, coarse_chunks_ids):
            for text in make_proxies(coarse_chunk):                 # ← 唯一的区别
                proxies.append(Document(page_content=text,
                                        metadata={doc_key: coarse_chunk_id}))

        retriever.vectorstore.add_documents(proxies)                        # 代理 → 向量库
        retriever.docstore.mset(list(zip(coarse_chunks_ids, coarse_chunks)))  # 父块 → 文档库
    return retriever

summary_retriever  = build_retriever("uk_summaries",
                                     lambda c: [summarization_chain.invoke(c)])
question_retriever = build_retriever("uk_hypothetical_questions",
                                     lambda c: hypothetical_questions_chain.invoke(c))

print(summary_retriever.invoke("Cornwall travel"))
print(question_retriever.invoke("How can you go to Brighton from London?"))

import { v4 as uuidv4 } from "uuid";
import { z } from "zod";
import { MultiVectorRetriever } from "@langchain/classic/retrievers/multi_vector";
import { InMemoryStore } from "@langchain/core/stores";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { StringOutputParser } from "@langchain/core/output_parsers";

const llm = new ChatOpenAI({ model: "gpt-5-nano" });
const docKey = "doc_id";

// —— ② 生成摘要 ——
const summarizationChain = ChatPromptTemplate
  .fromTemplate("Summarize the following document:\n\n{document}")
  .pipe(llm).pipe(new StringOutputParser());

// —— ③ 生成假设问题：用 Zod schema 做结构化输出 ——
const HypotheticalQuestions = z.object({
  questions: z.array(z.string()).describe("List of hypothetical questions for given text"),
});
const hypotheticalQuestionsChain = ChatPromptTemplate
  .fromTemplate("Generate a list of exactly 4 hypothetical questions that the below text " +
                "could be used to answer:\n\n{document_text}")
  .pipe(llm.withStructuredOutput(HypotheticalQuestions));

// —— 通用的入库流程：只有「代理怎么来」不同 ——
async function buildRetriever(
  collectionName: string,
  makeProxies: (chunk: Document) => Promise<string[]>,
) {
  const retriever = new MultiVectorRetriever({
    vectorstore: new Chroma(embeddings, { collectionName }),
    byteStore: new InMemoryStore<Uint8Array>(),
    idKey: docKey,
  });

  for (const url of ukDestinationUrls) {
    const coarseChunks = await parentSplitter.splitDocuments(await loadAsTextDocs(url));
    const ids = coarseChunks.map(() => uuidv4());

    const proxies: Document[] = [];
    for (const [i, chunk] of coarseChunks.entries()) {
      for (const text of await makeProxies(chunk)) {             // ← 唯一的区别
        proxies.push(new Document({ pageContent: text, metadata: { [docKey]: ids[i] } }));
      }
    }
    await retriever.vectorstore.addDocuments(proxies);                       // 代理 → 向量库
    await retriever.docstore.mset(coarseChunks.map((c, i) => [ids[i], c]));  // 父块 → 文档库
  }
  return retriever;
}

const summaryRetriever = await buildRetriever("uk_summaries",
  async (c) => [await summarizationChain.invoke({ document: c.pageContent })]);
const questionRetriever = await buildRetriever("uk_hypothetical_questions",
  async (c) => (await hypotheticalQuestionsChain.invoke({ document_text: c.pageContent })).questions);

console.log(await summaryRetriever.invoke("Cornwall travel"));
console.log(await questionRetriever.invoke("How can you go to Brighton from London?"));

    @UserMessage("""
            Generate a list of exactly 4 hypothetical questions that the below text
            could be used to answer:

            {{document_text}}""")

}

Indexer indexer = AiServices.create(Indexer.class, llm);

⚠ 这两种方法入库很慢、很贵

每个粗块都要调用一次 LLM。几百个块还好，几十万个块就是一笔可观的费用和时间。 实践中的建议：对外层循环做并行；把生成的摘要 / 问题持久化，别每次重建；先在小样本上验证确实有效，再全量跑。

🔬 结构化输出：with_structured_output

生成假设问题时，我们要的是一个字符串列表，而不是一段需要再解析的文字。 with_structured_output(Schema) 让模型按给定的结构返回对象（底层利用了模型的函数调用 / JSON 模式能力）。 它比第 4 章「在提示词里举例 + 手动 json.loads」可靠得多，后面的章节会大量使用。 Python 用 Pydantic 模型描述结构，TypeScript 用 Zod，Java 直接用方法的返回类型。

变体 ④：细块扩展

反过来想：检索仍然用细块，但命中之后，把它前后相邻的块也一起带上。 这相当于给命中的那句话配上「前情」和「后续」。 

granular_chunk_splitter = RecursiveCharacterTextSplitter(chunk_size=500)

multi_vector_retriever = MultiVectorRetriever(
    vectorstore=Chroma(collection_name="uk_granular_chunks", embedding_function=embeddings),
    byte_store=InMemoryByteStore())

for destination_url in uk_destination_urls:
    html_docs = AsyncHtmlLoader(destination_url).load()
    text_docs = html2text_transformer.transform_documents(html_docs)
    granular_chunks = granular_chunk_splitter.split_documents(text_docs)

    expanded_chunk_store_items = []
    for i, granular_chunk in enumerate(granular_chunks):
        # 取前一块、当前块、后一块（注意首尾边界）
        neighbours = granular_chunks[max(i - 1, 0): i + 2]
        expanded_chunk_text = "\n".join(c.page_content for c in neighbours)

        expanded_chunk_id = str(uuid.uuid4())
        expanded_chunk_store_items.append(
            (expanded_chunk_id, Document(page_content=expanded_chunk_text)))
        granular_chunk.metadata[doc_key] = expanded_chunk_id    # 细块指向它的扩展块

    multi_vector_retriever.vectorstore.add_documents(granular_chunks)      # 细块 → 向量库
    multi_vector_retriever.docstore.mset(expanded_chunk_store_items)       # 扩展块 → 文档库

  await expansionRetriever.docstore.mset(expandedItems);               // 扩展块 → 文档库

ⓘ 仓库原代码里的一个小瑕疵

Notebook 中判断是否有前一块用的是 if previous_chunk_num:。当 previous_chunk_num 为 0 时， Python 会把它当成「假」，于是第 1 块（下标 1）的扩展块会漏掉第 0 块。上面改用切片 [max(i-1, 0): i+2] 避开了这个问题 —— 这也是 Python 里「用 0 当布尔值」的经典陷阱。

半结构化内容：文字里夹着表格

PDF 和网页里经常是「几段文字 + 一张表格」。把表格当普通文字切块，行列关系就全乱了。更好的做法是分开处理：

拆分文字和表格可以用 unstructured 这类文档解析库。如果表格数据量大、需要精确的数值计算，更好的归宿是关系数据库，用第 10 章的 Text-to-SQL 来查。

多模态 RAG：资料里有图

当文档里有示意图、图表、照片时，常见的做法同样是「用文字代理去找，把原图交出去」：

  1. 入库：用多模态模型为每张图片生成一段文字描述，嵌入这段描述；原图存入文档库。
  2. 检索：问题与描述文字做语义匹配，取回对应的原图。
  3. 生成：把问题、相关文字和原图一起发给多模态模型作答。

另一条路是使用能把图片和文字映射到同一个向量空间的多模态嵌入模型，直接对图片做向量化。

小结

  • 基础 RAG 的问题可以归为六类；本章解决第一类：检索到的块不对或不完整。
  • 块大小是两难：小块匹配准但上下文少，大块上下文足但匹配被稀释。
  • 切分可以按文档结构（标题），也可以按大小（token、字符、递归）。最优方案只能靠实测。
  • 核心套路是把「匹配」和「阅读」拆开：向量库存小的代理，文档库存大的父块，用 ID 关联。
  • 四种变体：父子块、摘要嵌入、假设问题嵌入、细块扩展。前者和后者入库便宜，中间两种要为每块调用 LLM。
  • with_structured_output 让模型直接返回结构化对象。
  • 表格和图片同样适用这个套路：嵌入它们的文字描述，返回原始内容。
