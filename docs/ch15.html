第 15 章 · 原书之外的补充

上下文工程与评估

这一章不在原书里。它补上两个在原书成稿之后变得越来越重要的话题： 智能体跑得久了，上下文窗口里该放什么、不该放什么（上下文工程）； 以及改了一句提示词之后，怎么知道系统是变好了还是变坏了（评估）。 一个决定智能体能走多远，一个决定你敢不敢改它。

本章目标

  • 理解为什么「窗口装得下」不等于「应该全装进去」
  • 掌握管理上下文的四类手段：写出去、选进来、压缩、隔离
  • 用现成的中间件实现裁剪、摘要和工具结果清理
  • 知道评估智能体要看哪三个层面
  • 搭一个最小的评估流程：数据集 → 运行 → 打分 → 对比
ⓘ 关于这一章的代码

本章没有对应的仓库代码。示例依据 2026 年 10 月时 LangChain、LangSmith 的官方文档编写，三种语言的版本都没有实际运行验证， 请当作思路示意。

从提示词工程到上下文工程

第 2 章学的提示词工程，关心的是「这一段话怎么写」。那时候上下文很简单：一条系统消息，一个问题。

到了智能体，情况变了。看看第 12 章那个 Supervisor 跑到第十步时，发给模型的内容里都有什么：

为什么不能全塞进去

现在的模型动辄几十万甚至上百万 token 的窗口，为什么还要费心管理？因为上下文太长会带来四个问题：

🫧

注意力被稀释

内容越多，模型越难抓住重点。放在一长段中间的信息尤其容易被忽略 —— 这个现象被称为「迷失在中间」。

💥

被旧信息带偏

早先一次失败的工具调用、一段已经作废的计划留在历史里，模型可能反复受它影响。

💸

贵

ReAct 循环的每一圈都要把全部上下文重新发一遍。上下文翻倍，整个任务的费用不止翻倍。

🐢

慢

输入越长，首个 token 来得越晚。

🔑 把上下文当成稀缺资源

目标不是「尽量多给」，而是用尽可能少的、信息密度尽可能高的 token，换来想要的行为。 前面各章其实一直在做这件事：RAG 只取最相关的几块（第 6 章），父子块检索控制交给模型的粒度（第 8 章）， 检索后处理丢掉无关结果（第 10 章），拆分智能体让每个只带少量工具（第 12 章）。这一章把它们放进一个统一的框架里看。

四类手段

手段本教程里已经出现过的例子现成的工具
写出去LangGraph 的状态字段（第 5 章）；检查点（第 14 章）Deep Agents 的文件工具；LangGraph Store
选进来整个 RAG 部分（第 6–10 章）检索器；LLMToolSelectorMiddleware
压缩Map-Reduce 摘要（第 3 章）；记忆窗口（第 7 章）SummarizationMiddleware、ContextEditingMiddleware、trim_messages
隔离多智能体（第 12 章）子智能体即工具；Deep Agents 的 subagents

压缩：三种力度

压缩最常用，也最容易出错（压掉了不该压的）。按从轻到重排列：

清理旧的工具结果

最划算的一招。工具结果往往是上下文里最大的一块，而且用过即可丢 —— 模型已经根据它得出了结论，结论还在对话里，原始数据不必一直留着。

裁剪旧消息

只保留最近的若干条。简单、零成本，但会彻底忘记早期内容。注意不能从中间随便切： 一条带工具调用请求的 AI 消息和它对应的工具结果必须成对出现，否则模型接口会报错。用库函数而不是自己切列表。

摘要

把旧消息交给一个便宜的模型，压成一段摘要，再接上最近的消息。保住了要点，代价是一次额外的模型调用，以及摘要可能漏掉某个后来才显得重要的细节。

// 摘要：没有现成的类，自己实现也不复杂 —— 超过阈值时，把较早的消息交给小模型总结。
interface Summarizer {
    @UserMessage("""
            Summarize the conversation below. Keep every fact, decision, name, date and
            number that may be needed later. Be concise.

            {{conversation}}""")
    String summarize(@V("conversation") String conversation);
}

static List<ChatMessage> compact(List<ChatMessage> messages, Summarizer summarizer, int keepLast) {
    if (messages.size() <= keepLast + 10) return messages;          // 还不够长，不动

    List<ChatMessage> old    = messages.subList(0, messages.size() - keepLast);
    List<ChatMessage> recent = messages.subList(messages.size() - keepLast, messages.size());

    String summary = summarizer.summarize(
            old.stream().map(Object::toString).collect(Collectors.joining("\n")));

    List<ChatMessage> compacted = new ArrayList<>();
    compacted.add(SystemMessage.from("Summary of the earlier conversation:\n" + summary));
    compacted.addAll(recent);                                        // 最近的消息保持原样
    return compacted;
}
⚠ 压缩是有损的，而且损失是悄悄发生的

摘要丢了一个日期，用户三轮之后问到时才会暴露。所以：阈值不要设得太激进；摘要提示词里明确要求保留事实、数字、名字和已做的决定； 最要紧的信息（用户的硬性约束、任务目标）不要只留在对话历史里 —— 把它们写出去，放进状态字段或文件，每一步明确地带进来。

写出去与隔离：给长任务用的两招

写出去：把窗口当工作台，而不是仓库

一次网页搜索返回 2 万字。让它一直躺在上下文里，后面每一步都要为它付费。更好的做法是： 工具把全文存成文件，只返回一小段摘要和文件路径；模型需要细节时再读文件的某一部分。

from langchain_core.tools import tool

def fetch_page(url: str) -> str:

            f"Preview:\n{text[:500]}")                       # 进入上下文的只有这 500 字

@tool(description="Read part of a saved file. offset and limit are in characters.")
def read_file(path: str, offset: int = 0, limit: int = 3000) -> str:
    return Path(path).read_text(encoding="utf-8")[offset: offset + limit]

public class WorkspaceTools {
    private final Path workspace = Path.of("./workspace");

    @Tool("Fetch a web page. Saves the full text to a file and returns a short preview "
        + "plus the file path. Use readFile to see more of the content.")
    public String fetchPage(@P("URL of the page") String url) throws IOException {
        String text = WebScraping.webScrape(url);                    // 第 4 章的抓取函数
        Files.createDirectories(workspace);
        Path path = workspace.resolve(Integer.toHexString(url.hashCode()) + ".txt");
        Files.writeString(path, text);
        return "Saved %d characters to %s.%nPreview:%n%s".formatted(
                text.length(), path, text.substring(0, Math.min(500, text.length())));
    }

    @Tool("Read part of a saved file. offset and limit are in characters.")
    public String readFile(@P("File path") String path,
                           @P("Start offset") int offset,
                           @P("Max characters") int limit) throws IOException {
        String text = Files.readString(Path.of(path));
        return text.substring(Math.min(offset, text.length()),
                              Math.min(offset + limit, text.length()));
    }
}
⚠ 给智能体文件读写能力时要设边界

上面的 read_file 为了简短，接受任意路径。真实系统里必须把路径限制在工作目录之内（解析成绝对路径后检查前缀）， 否则模型（或藏在网页里的恶意指令）可以让它去读密钥文件。Deep Agents 之类的框架用「虚拟文件系统」和沙箱来解决这个问题。

隔离：子智能体是一次性的干净窗口

第 12 章从「分工」的角度讲多智能体，这里换一个角度看：子智能体的最大价值是上下文隔离。 它在自己的窗口里折腾几十步、读几万字，这些都不会进入主智能体的上下文 —— 主智能体只收到一段结论。

这也解释了给子智能体派任务时的两条纪律：

  • 任务说明必须自成一体。子智能体看不到主对话，「查一下那里的酒店」对它毫无意义 —— 要写成「查 Newquay 两人入住、7 月 12–15 日的酒店」。
  • 让它返回结论，而不是过程。在子智能体的提示词里写明要返回什么格式的结果，否则隔离就白做了。

一个省钱的细节：让上下文的开头保持稳定

多数模型供应商提供提示词缓存：如果这次请求的开头部分和最近某次请求一字不差，这部分的输入费用大幅打折，速度也更快。 智能体循环的每一圈都以同样的系统提示词和工具清单开头，天然适合缓存 —— 前提是你别破坏它：

会让缓存失效的做法
  • 在系统提示词开头写「现在是 14:32:07」
  • 每次请求以不同顺序列出工具
  • 修改或重排历史消息中靠前的部分
缓存友好的做法
  • 不变的内容放最前，经常变的（时间、检索结果）往后放
  • 工具清单的顺序固定
  • 历史只在末尾追加；需要压缩时一次压一大段，而不是每轮动一点

第 13 章提到的 2026 版 MCP 规范要求服务器以确定的顺序返回工具列表，原因之一正是为了提高缓存命中率。

评估：给智能体做体检

你把系统提示词里的一句话改得更清楚了，手动试了三个问题，都不错，于是上线。第二天发现另一类问题的回答全乱了。 LLM 应用的行为没法靠「看代码」推断，唯一的办法是跑一遍看结果 —— 评估就是把「跑一遍看结果」变成可重复的流程。

看哪三个层面

层面问的问题例子怎么评
最终答案结果对不对？回答里的酒店名和价格与数据库一致吗与参考答案比对；LLM 裁判
单步某一步的决定对不对？问天气时，第一步选的是天气工具吗？参数是镇名吗代码规则，精确、便宜
轨迹整条路走得合理吗？有没有重复调用、绕远路、漏掉必要步骤与期望的工具序列比较；LLM 裁判

只看最终答案会漏掉很多问题：答案碰巧对了，但它是跳过检索凭记忆答的（第 11 章见过）。所以智能体至少要同时评「答案」和「用了哪些工具」。

三种评估器

代码规则

精确匹配、包含某个关键词、输出是合法 JSON、调用了指定工具。能用代码判断的，一律用代码：快、免费、结果稳定。

LLM 当裁判

「回答是否与参考答案一致？」「是否只依据了给定资料？」这类需要理解语义的判断，交给另一个模型打分。

人工

最准也最贵。主要用来校准 LLM 裁判：抽一批样本人工打分，看裁判和人的判断一致率有多高。

最小可用的评估流程

// —— ② 被测系统 ——
async function target(inputs: Record<string, any>) {
  const result = await travelInfoAgent.invoke({
    messages: [{ role: "user", content: inputs.question }] });
  const toolsUsed = result.messages.flatMap((m: any) => (m.tool_calls ?? []).map((c: any) => c.name));
  return { answer: result.messages.at(-1)?.text ?? "", tools_used: toolsUsed };

type EvalArgs = { inputs: Record<string, any>; outputs: Record<string, any>;
                  referenceOutputs?: Record<string, any> };

// —— ③a 代码评估器：用对工具了吗 ——
function usedExpectedTools({ outputs, referenceOutputs }: EvalArgs): EvaluationResult {
  const used = new Set(outputs.tools_used);
  const score = (referenceOutputs?.expected_tools ?? []).every((t: string) => used.has(t));
  return { key: "used_expected_tools", score };
}

    "The assistant answer is correct if it is consistent with the reference and does " +
    "not contradict it. Extra correct detail is fine.");
  return { key: "answer_is_correct", score: grade.correct, comment: grade.reasoning };
}

// —— ④ 运行 ——
await evaluate(target, {
  data: datasetName,
  evaluators: [usedExpectedTools, answerIsCorrect],
  experimentPrefix: "gpt-4.1-mini, system prompt v2",
  maxConcurrency: 4,
});

// 没有平台也能评估：数据集是一个列表，评估是一个循环。放进 JUnit，就能在 CI 里跑。
record Example(String question, String referenceAnswer, List<String> expectedTools) {}
record Grade(String reasoning, boolean correct) {}

interface Judge {                                    // ③b LLM 裁判
    @UserMessage("""
            You are grading an AI travel assistant.
            Question: {{question}}
            Reference answer: {{reference}}
            Assistant answer: {{answer}}
            The assistant answer is correct if it is consistent with the reference and does
            not contradict it. Extra correct detail is fine.""")
    Grade grade(@V("question") String q, @V("reference") String ref, @V("answer") String ans);
}

List<Example> dataset = List.of(                      // ① 数据集
        new Example("What can I see in Penzance?",
                "St Michael's Mount, the promenade, Jubilee Pool ...", List.of("searchTravelInfo")),
        new Example("What's the weather like in St Ives?",
                "Current conditions for St Ives from the weather tool.", List.of("weatherForecast")),
        new Example("Write me a Python sorting function.",
                "A polite refusal: only Cornwall travel questions are supported.", List.of()));

Judge judge = AiServices.create(Judge.class, judgeModel);
int toolsOk = 0, answersOk = 0;

for (Example ex : dataset) {
    var recorder = new ToolCallRecorder();            // 一个记录工具调用名称的监听器（自己实现）
    String answer = buildAgent(recorder).chat(ex.question());                     // ② 运行

    boolean usedTools = recorder.toolNames().containsAll(ex.expectedTools());     // ③a 代码评估器
    Grade grade = judge.grade(ex.question(), ex.referenceAnswer(), answer);

    if (usedTools) toolsOk++;
    if (grade.correct()) answersOk++;
    else System.out.println("FAIL: " + ex.question() + " — " + grade.reasoning());
}

// ④ 汇总。把这两个数字和上一次的结果比较，或者在测试里设一个不许跌破的下限。
System.out.printf("tools: %d/%d, answers: %d/%d%n", toolsOk, dataset.size(), answersOk, dataset.size());

让裁判靠谱

LLM 裁判本身也是一个需要调试的提示词。几条经验：

  • 一次只判一件事。「正确吗」和「语气得体吗」分成两个评估器，不要让它打一个综合分。
  • 用是 / 否，不用 1–10 分。模型对「7 分还是 8 分」并不稳定，二元判断可靠得多。
  • 先写理由，再给结论。上面的 Grade 把 reasoning 放在 correct 前面 —— 第 2 章的思维链在这里同样有效，而且理由能帮你排查裁判为什么判错。
  • 定期和人工对一对。抽 30 条人工打分，裁判与人的一致率不高时，先修裁判，再信它的分数。

离线评估与在线评估

离线评估在线评估
数据事先准备的数据集，有参考答案真实的线上流量，没有参考答案
什么时候跑每次改提示词、换模型、升级依赖之后；放进 CI持续进行，对线上追踪记录抽样打分
能发现改动有没有把原来好的东西搞坏（回归）数据集没覆盖到的新问题；质量随时间的漂移
评估器与参考答案比对不需要参考答案的检查：是否有依据、是否拒答、用户有没有点踩

两者是接力关系：在线评估发现坏例子 → 补进离线数据集 → 修复 → 离线评估确认修好且没有引入新问题。

💡 评估集从哪来

不用等「准备充分」。从 20 条开始：十条最常见的问题，五条你知道容易出错的边界情况，五条应该被拒绝的问题。 之后每遇到一个线上的坏回答，就把它加进去。半年后你会有一份真正反映自己业务的测试集 —— 这比任何公开榜单都更能告诉你该不该换模型。

小结

  • 上下文工程：在模型的每一步，让窗口里恰好有这一步需要的信息。提示词工程是它的一部分。
  • 上下文过长会稀释注意力、被旧信息带偏，而且又贵又慢 —— 窗口装得下不等于应该装。
  • 四类手段：写出去（存到窗口之外）、选进来（按需取回）、压缩（清理、裁剪、摘要）、隔离（子智能体）。
  • 压缩按力度从轻到重：清理旧工具结果 → 裁剪旧消息 → 摘要。压缩有损，关键信息要另外保存。
  • 子智能体的核心价值是上下文隔离；任务说明要自成一体，返回要只含结论。
  • 让上下文的开头保持稳定，可以利用提示词缓存省钱提速。
  • 评估是「数据集 → 运行 → 打分 → 对比」的可重复流程；智能体要同时评最终答案、单步决定和整条轨迹。
  • 能用代码判断的用代码；语义判断交给 LLM 裁判，并用人工抽查校准它。
  • 离线评估防回归，在线评估发现新问题，两者接力。

动手练习

  1. 和第 12 章的 Supervisor 连续聊十轮，在 LangSmith 里查看最后一次模型调用的输入 token 数，并估算各部分（系统、工具说明、历史、工具结果）各占多少。
  2. 给它加上清理工具结果的中间件，重复第 1 题，对比 token 数和回答质量。
  3. 把摘要的触发阈值设得很低，早早告诉它一个细节（比如「我对花生过敏」），聊到触发摘要之后再问一个依赖这个细节的问题。它还记得吗？怎么改能让它一定记得？
  4. 为你的旅行助手写 20 条评估样例，跑一次评估得到基线分数。
  5. 故意把系统提示词里「Only use the tools to find the information you need」这句删掉，再跑一次评估。哪个评估器的分数变了？
  6. 抽 10 条让 LLM 裁判打分的结果，自己也打一遍分。你们在哪几条上意见不同？是它错了还是参考答案写得不清楚？
