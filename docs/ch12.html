第 12 章

多智能体系统

一个智能体挂上二三十个工具之后，就像一个身兼数职的员工：容易拿错工具，提示词越写越长，改一处怕影响另一处。 解法和管理团队一样 —— 分工。这一章把旅行助手拆成两个各司其职的智能体， 再用两种方式把它们组织起来：路由器和主管（Supervisor）。

本章目标

  • 知道什么时候该把一个智能体拆成多个
  • 构建第二个智能体：住宿预订（查酒店数据库 + 查民宿接口）
  • 用路由器模式把问题分发给合适的智能体
  • 理解路由器的局限，并用 Supervisor 模式处理跨领域的问题
  • 在两种模式之间做出取舍

为什么要多个智能体

一个全能智能体
  • 工具越多，模型越容易选错
  • 系统提示词要兼顾所有场景，又长又互相打架
  • 每次调用都带着全部工具的说明书，费 token
  • 改动任何一处，都要回归测试全部功能
多个专职智能体
  • 每个智能体只有少量相关工具，选得准
  • 提示词短而聚焦
  • 可以为不同任务选不同档位的模型
  • 可以独立开发、测试、替换

构建住宿预订智能体

它需要查两类住宿，数据来源完全不同 —— 正好演示工具可以包装任何东西：

酒店：直接用现成的 SQL 工具包

酒店数据在 SQLite 数据库里（hotel_db/cornwall_hotels_schema.sql，包含 hotels 和 hotel_room_offers 两张表）。 第 10 章我们手写了 Text-to-SQL 链；在智能体里更省事 —— LangChain 的 SQLDatabaseToolkit 直接给出一组工具：

工具作用
sql_db_list_tables列出有哪些表
sql_db_schema查看指定表的结构和几行样例数据
sql_db_query_checker让 LLM 检查一条 SQL 有没有常见错误
sql_db_query执行 SQL 并返回结果

智能体会自己串起这些工具：先看有哪些表 → 看表结构 → 写 SQL → 检查 → 执行。如果执行报错，它能读到错误信息并自己改正重试。 这比固定的 Text-to-SQL 链更健壮，代价是多几次模型调用。

public class BookingTools {
    record BnBOffer(int bnbId, String bnbName, String town, int availableRooms, double pricePerRoom) {}

    private static final List<BnBOffer> MOCK_BNB_OFFERS = List.of(
            new BnBOffer(1, "Seaside BnB", "Newquay", 3, 80.0),
            new BnBOffer(7, "Penzance Pier BnB", "Penzance", 2, 95.0) /* ……更多 */);

    private static final String DB_URL = "jdbc:sqlite:file:hotel_db/cornwall_hotels.db?mode=ro";   // 只读

    @Tool("Get the schema (CREATE TABLE statements) of the Cornwall hotels database.")
    public String hotelDbSchema() throws SQLException {
        return runQuery("SELECT sql FROM sqlite_master WHERE type = 'table' AND sql IS NOT NULL");
    }

    @Tool("Run a SQLite SELECT query against the Cornwall hotels database. "
        + "Call hotelDbSchema first to learn the table structure.")
    public String hotelDbQuery(@P("A single SQLite SELECT statement") String sql) {
        if (!sql.trim().toLowerCase().startsWith("select")) return "Error: only SELECT statements are allowed.";
        try { return runQuery(sql); }
        catch (SQLException e) { return "Error: " + e.getMessage(); }   // 模型会读到错误并重试
    }

    @Tool("Check BnB room availability and price for a destination in Cornwall.")
    public Object checkBnbAvailability(@P("Town in Cornwall") String destination,
                                       @P("Number of rooms needed") int numRooms) {
        var offers = MOCK_BNB_OFFERS.stream()
                .filter(o -> o.town().equalsIgnoreCase(destination) && o.availableRooms() >= numRooms)
                .toList();
        return offers.isEmpty()
                ? Map.of("error", "No available BnBs found in " + destination + " for " + numRooms + " rooms.")
                : offers;
    }

    private String runQuery(String sql) throws SQLException { /* JDBC：执行并把结果拼成文本，见第 10 章 */ }
}

现在有了两个可以独立运行的智能体。问题是：用户发来一句话，该交给谁？

模式一：路由器

最简单的协调方式：在最前面放一个路由节点，判断问题属于哪个领域，然后把控制权整个交给对应的智能体。 智能体处理完，直接结束。 

from enum import Enum
from pydantic import BaseModel, Field
from langgraph.types import Command
from langgraph.graph import StateGraph, END

class AgentType(str, Enum):
    travel_info_agent = "travel_info_agent"
    accommodation_booking_agent = "accommodation_booking_agent"

class AgentTypeOutput(BaseModel):
    agent: AgentType = Field(..., description="Which agent should handle the query?")

llm_router = llm_model.with_structured_output(AgentTypeOutput)

ROUTER_SYSTEM_PROMPT = (
    "You are a router. Given the following user message, decide if it is a travel "
    "information question (about destinations, attractions, or general travel info) "
    "or an accommodation booking question (about hotels, BnBs, room availability, or prices).\n"
    "If it is a travel information question, respond with 'travel_info_agent'.\n"
    "If it is an accommodation booking question, respond with 'accommodation_booking_agent'."
)

def router_agent_node(state: AgentState) -> Command[AgentType]:
    """路由节点：决定由哪个智能体处理用户的问题。"""
    last_msg = state["messages"][-1] if state["messages"] else None
    if isinstance(last_msg, HumanMessage):
        router_response = llm_router.invoke([
            SystemMessage(content=ROUTER_SYSTEM_PROMPT),
            HumanMessage(content=last_msg.content)])
        return Command(goto=router_response.agent.value)       # 跳转到被选中的节点
    return Command(goto=AgentType.travel_info_agent.value)     # 兜底

graph = StateGraph(AgentState)
graph.add_node("router_agent", router_agent_node)
graph.add_node("travel_info_agent", travel_info_agent)                       # 编译好的智能体可以直接当节点
graph.add_node("accommodation_booking_agent", accommodation_booking_agent)
graph.add_edge("travel_info_agent", END)
graph.add_edge("accommodation_booking_agent", END)
graph.set_entry_point("router_agent")
travel_assistant = graph.compile()

import { Command, MessagesAnnotation, StateGraph, START, END } from "@langchain/langgraph";
import { z } from "zod";

const AGENTS = ["travel_info_agent", "accommodation_booking_agent"] as const;

const llmRouter = llmModel.withStructuredOutput(z.object({
  agent: z.enum(AGENTS).describe("Which agent should handle the query?"),
}));

const ROUTER_SYSTEM_PROMPT =
  "You are a router. Given the following user message, decide if it is a travel " +
  "information question (about destinations, attractions, or general travel info) " +
  "or an accommodation booking question (about hotels, BnBs, room availability, or prices).\n" +
  "If it is a travel information question, respond with 'travel_info_agent'.\n" +
  "If it is an accommodation booking question, respond with 'accommodation_booking_agent'.";

/** 路由节点：决定由哪个智能体处理用户的问题。 */
async function routerAgentNode(state: typeof MessagesAnnotation.State) {
  const lastMsg = state.messages.at(-1);
  if (lastMsg instanceof HumanMessage) {
    const { agent } = await llmRouter.invoke([
      new SystemMessage(ROUTER_SYSTEM_PROMPT),
      new HumanMessage(lastMsg.content as string)]);
    return new Command({ goto: agent });                   // 跳转到被选中的节点
  }
  return new Command({ goto: "travel_info_agent" });       // 兜底
}

export const travelAssistant = new StateGraph(MessagesAnnotation)
  .addNode("router_agent", routerAgentNode, { ends: [...AGENTS] })   // 声明它可能跳去哪
  .addNode("travel_info_agent", travelInfoAgent)                     // 智能体直接当节点
  .addNode("accommodation_booking_agent", accommodationBookingAgent)
  .addEdge(START, "router_agent")
  .addEdge("travel_info_agent", END)
  .addEdge("accommodation_booking_agent", END)
  .compile();

enum AgentType {
    @Description("Travel information questions: destinations, attractions, weather, general travel info")
    TRAVEL_INFO_AGENT,
    @Description("Accommodation booking questions: hotels, BnBs, room availability, prices")
    ACCOMMODATION_BOOKING_AGENT
}

interface Router {
    @SystemMessage("You are a router. Decide which agent should handle the user message.")
    AgentType route(String userMessage);
}

/** 路由器模式：先分类，再把问题整个交给被选中的智能体。 */
class RouterAssistant {
    private final Router router;
    private final TravelInfoAgent travelInfoAgent;
    private final AccommodationBookingAgent bookingAgent;

    RouterAssistant(ChatModel llm, TravelInfoAgent travelInfoAgent, AccommodationBookingAgent bookingAgent) {
        this.router = AiServices.create(Router.class, llm);
        this.travelInfoAgent = travelInfoAgent;
        this.bookingAgent = bookingAgent;
    }

    String chat(String userMessage) {
        return switch (router.route(userMessage)) {
            case TRAVEL_INFO_AGENT           -> travelInfoAgent.chat(userMessage);
            case ACCOMMODATION_BOOKING_AGENT -> bookingAgent.chat(userMessage);
        };
    }
}

两个值得注意的新东西：

  • 智能体可以当节点用。create_react_agent 返回的是一个编译好的图，而图本身可以作为另一个图的节点（子图）。这就是「组合」。
  • Command(goto=...)：节点除了返回状态更新，还可以直接指定「下一步去哪个节点」。它把第 5 章的「条件边 + 路由函数」合二为一，写起来更直接。

路由器的硬伤

再问一个跨领域的问题：

You: Find me a beach town in Cornwall with nice weather, and tell me which hotels have rooms there.

这句话同时需要两个智能体：先找天气好的海滨小镇（信息），再查那里的酒店（预订）。 但路由器只能二选一，而且交出去就不回来 —— 无论选谁，都只能回答一半。

模式二：Supervisor（主管）

解决办法是让协调者不退场：它把任务派给一个智能体，等结果回来， 再决定下一步 —— 派给另一个智能体，还是已经可以回答用户了。这就是 Supervisor 模式，「智能体的智能体」。

注意第 ③ 步：主管把第 ② 步得到的镇名带进了给预订智能体的任务里。能在智能体之间传递中间结果，正是 Supervisor 比路由器强的地方。

🔬 create_supervisor 在背后做了什么

它为每个子智能体自动生成一个「移交」工具（类似 transfer_to_travel_info_agent）， 然后创建一个拥有这些工具的 ReAct 智能体作为主管。主管「调用工具」的效果是跳转到对应的子智能体节点； 子智能体跑完后，有一条固定的边回到主管。 所以它仍然是第 11 章的那个循环 —— 只是「工具」换成了「另一个智能体」。Java 版把这层关系直接写在了明面上。

两种模式怎么选

路由器Supervisor
交互方式单程：分发后不再参与往返：每个子任务完成后回到主管
能否处理跨领域问题不能能，且可以把前一步结果传给后一步
额外的 LLM 调用1 次（分类）多次（每次派发、每次汇总都要调用主管）
延迟与成本低高，且主管通常需要更强的模型
可预测性高较低（主管自己规划路径）
适合问题通常只属于一个领域；对延迟敏感经常需要多个专家协作完成一个请求
💡 从简单的开始

如果 95% 的用户问题只涉及一个领域，路由器就够了 —— 更快、更便宜、更容易调试。 等真的出现大量跨领域问题，再升级到 Supervisor。两者甚至可以组合： 先用路由器快速分流，只有被判断为「复杂」的请求才交给 Supervisor。

还有哪些多智能体结构

层级式（Hierarchical）

主管下面还有主管，每个小主管带一组专家。适合智能体数量很多的大型系统。

群体式（Swarm / Handoff）

没有中心协调者，智能体之间可以直接互相移交对话控制权，像客服之间的转接。

流水线式

智能体按固定顺序接力：研究员 → 写手 → 审稿人。本质上是第 5 章的工作流，只是每个节点是一个智能体。

用 LangSmith 看多智能体的执行

多智能体系统的追踪记录是一棵更深的树。以那个跨领域问题为例，你会看到类似这样的结构：

travel_assistant（supervisor）
├─ supervisor: LLM → 决定调用 transfer_to_travel_info_agent
├─ travel_info_agent
│   ├─ LLM → tool_calls: search_travel_info("beach towns in Cornwall")
│   ├─ tools: search_travel_info
│   ├─ LLM → tool_calls: weather_forecast("Newquay"), weather_forecast("St Ives")
│   ├─ tools: weather_forecast ×2
│   └─ LLM → "Newquay is sunny, 24°C ..."
├─ supervisor: LLM → 决定调用 transfer_to_accommodation_booking_agent
├─ accommodation_booking_agent
│   ├─ LLM → tool_calls: sql_db_list_tables
│   ├─ ……（看表结构、写 SQL、执行）
│   ├─ LLM → tool_calls: check_bnb_availability("Newquay", 1)
│   └─ LLM → "Hotels with rooms in Newquay: ..."
└─ supervisor: LLM → 综合两份结果，给出最终答案

一次用户请求，背后可能是十几次模型调用。这也提醒我们：多智能体不是免费的午餐，每增加一层协调，延迟和费用都会上升。

小结

  • 工具太多、职责太杂时，把一个智能体拆成多个专职智能体：工具选得更准，提示词更聚焦，便于独立演进。
  • 工具可以包装任何东西：向量库、SQL 数据库（现成的工具包）、REST 接口。
  • 编译好的智能体可以直接作为另一个图的节点（子图）。
  • 路由器模式：分类后单程移交。简单、快、便宜，但处理不了需要多个智能体协作的问题。
  • Supervisor 模式：主管反复派发任务并收回结果，能串联多个智能体、传递中间结果。更强，也更慢更贵。
  • Supervisor 的本质是「把智能体当工具用」的 ReAct 循环。
  • 先用最简单的结构满足需求，确有必要再加协调层。

  2. 在路由器版本里问那个跨领域问题，看它被路由到了哪个智能体，回答缺了什么。

  4. 给路由器加一个 "both" 选项：当问题跨领域时，先后调用两个智能体再合并答案。这和 Supervisor 相比，差在哪里？
  5. 新增第三个智能体「交通智能体」（工具可以是模拟的火车时刻查询），并把它接入 Supervisor。你需要改几处代码？
